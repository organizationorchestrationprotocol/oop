# Context controller and runtime adapter

The official controller in `dist/oop-enforce.js` implements `oop-context-1`. The manifest and interface describe the registered workspace, the bounded event envelope and the nonblocking response. Native integrations deliver additional context at supported session-opening and prompt events. Host authorization and effect verification apply independently.

## Contact points

Run the official controller as <execution-facility> <controller> <absolute-owned-runtime-root> <command>. Native definitions use command enforcement and bounded native JSON on standard input. Direct commands are session_open, prompt, record, snapshot and acquire. Native operation_entry and operation_completion preserve actual operation categories without opening user turns or advancing semantic revisions. Every command loads both root components through the module loader before dispatch; absent/invalid components terminate with explicit safe diagnostics. The root adapter exports exactly manifest and decodeEvent. The controller alone selects literal native-event alternatives and renders documented stdout/stderr/exit_code templates with typed single-pass placeholders. Actual host documentation determines argument expression/vector syntax, OS overrides and continuation status.

Every decoded session_open or prompt invocation writes one immutable response file, <owned-scope>/context/<session_key>/<response_id>.json, containing the outcome, diagnostics, instructions and complete context, and delivers a bounded acquisition instruction with its absolute locator. Authorized acquisition and validation remain permitted; unchanged material dependencies do not restart recovery. Compact responses identify immutable procedure definitions and an explicit lossless merge rule. The root-first acquire command returns ordered complete UTF-8 segments with owning chat, transaction, target, dependency identity, content identity, offsets and total bytes; missing definitions, invalidation and expiry remain explicit failures. It never authorizes resuming work the user stopped. The session file <session_key>.json keeps bounded state, an index of the 16 latest responses and the 16 latest diagnostics with their response identifiers; responses without a session identity go to unbound/. Files are compact UTF-8 JSON with structural newlines and lines of at most 4096 bytes. Definition files use content-derived names in the same owning session folder; indexed and actively acquired responses retain their definition closure. If the named file is missing or does not match the current turn, invoke snapshot and report the limitation. Present every diagnostic with its effective-language translation; no acknowledgment command exists. Direct record and snapshot diagnostics are returned only on standard output. Rejected records list diagnostic.items {field, rule, expected, received}; transition rejections add diagnostic.current {turn, version, subject_state, allowed_states}. Correct exactly those fields and resubmit with a fresh request_id. An observed owned error journal is retired once its lock is absent, with the discarded unread count disclosed in session_errors. At every native write the controller prunes, under the session lock, orphan temporary files, sessions idle beyond 30 days, oversize files, responses outside the index older than 24 hours and the oldest inactive sessions beyond 128 sessions or 32 MiB; it never removes the current session, a session active within 24 hours or an indexed response, and reports over_soft_limit instead of refusing a session. Local exclusive lock files are never stolen on a timeout; reconcile orphan ownership before repair.

The runtime uses the current turn and version to report a reachable classified transition. Event text and full transcripts stay outside the context history. The controller renders shared workspace and organization instruction layers from scoped references and maintains a derived read-only view under common private state. Missing or invalid references are reflected in contextual diagnostics.

Invoke direct record and snapshot commands on the official controller with the same runtime root. Record requires event, chat, request_id, subject, turn, expected_version, state, level, related_ticket, facets and relation. The procedure supplies a typed schema and an example payload accepted as is once its values are replaced by the actual classification; a new subject starts from a state reachable from intake and is never submitted as intake, each later record uses the version of the last accepted receipt, and inapplicable optional fields are omitted rather than null. Direct record and snapshot responses carry the procedure by identity plus its dynamic parts and a one-line additionalContext; the complete procedure with that identity is reconstructible from the native response and its identified immutable definitions. Invalid/missing fields, unknown fields, unresolved material facets and stale transitions cannot become accepted defaults. The decoder handles only native enforcement; direct calls do not depend on a fabricated native event.

For every new subject, including G0, submit the classification before its substantive answer or dependent effect. Reuse the subject for continuations or clarifications, use the actual new turn after a prompt and reassess scope changes. Record only applicable reachable transitions; a new-turn subject begins at intake. G0 needs no artificial ticket or organizational event. Multiple subjects share a chat revision and retain independent current-turn states. Level, ticket relation and classification remain attributed claims, not effect authority.

Delivered `additionalContext` contains the actual executable/argument vector, owned registration, native chat, current turn/revision, input template with runtime-selected fields, known facet vocabulary, module-loading instructions, timing, acceptance and recovery. Bootstrap, adoption, missing shared instructions and unavailable context carry applicable procedure locators and next actions. A module name or instruction to classify alone does not satisfy delivery.

Inspect the actual `oop_context` envelope and source/interface binding. Acceptance requires `context.status=record_accepted` and a matching `context.receipt.disposition=accepted`, installation UID, chat, request ID, subject, turn, selected state/level, ticket relation, facets, relation and resulting version. First acceptance advances `expected_version` by one. An exact retained replay returns its original receipt without advancing state; a changed payload under that request ID is a correlation conflict. An accepted old-turn receipt cannot accept a current transition. Exit 0, well-formed output or text in chat is insufficient.

Use `snapshot` with `{event:'snapshot',chat:<actual-native-chat>}` after stale, busy, timeout or lost-response outcomes, or when the named native response file is missing or stale. It reads current state and bounded receipts without a new turn, daily synchronization or shared-instruction rewrite. Reconcile a matching receipt before retrying. A missing expired receipt does not prove failure. Preserve concurrent facts; changed payload requires a fresh request ID. Missing acceptance blocks dependent recorded-completion claims, while independent authorized work continues with the limitation disclosed. Retention is 16 history entries, 16 subjects and 32 receipts per chat, with the session-store pruning bounds above.

Turn state follows UX-09: a prompt opens an active turn; a decoded turn_stop with origin user or unknown marks it interrupted and with origin model closes it, never downgrading a user stop. A turn_stop emits only its declared context-free template (mode none), so it carries no context, continuation signal or veto; records for an interrupted turn are rejected with turn_interrupted, and the next prompt reports prior_turn in its response file. A native event that the adapter cannot decode emits empty output with exit 0; its stored outcome is counted in unbound_diagnostics at the next session opening or prompt. A decoded session opening or prompt that fails later preserves documented continuation and still delivers the reading instruction; the named response file carries the bounded actionable diagnostic. If no response file can be written, the instruction names the attempted locator or the storage limitation. Direct record/snapshot commands emit normalized JSON; record exits 0 only for an accepted receipt and otherwise 1, so callers must still inspect correlation. No diagnostic contains raw prompts, secrets, native payloads or arbitrary error text.

## Operations binding

The owned registration records the repository-scoped operations binding verified at bootstrap as operations_binding {profile, entries:[{entry, key, value}]}; dist/procedures/operations-binding.json maps the abstract entries to a version control system. At session opening and at the first prompt of the day the controller compares the checkout configuration with that record, read-only, and reports operations_binding {status: verified | drift | unavailable | not_recorded, items}. It never blocks or repairs; the runtime restores drifted entries under current authority before effects on operations.

## Daily synchronization and adoption

The first eligible event outside bootstrap inspects the exact configured checkout and synchronizes the selected official revision under a shared lock. The supplied version control implementation preserves branch references, replaces unpersisted checkout state, and leaves separate project data outside the operation. Unsupported topology, unknown ownership, interrupted work or transport failure remain observable. An orphan lock requires authorized reconciliation and evidence that the old writer cannot resume.

A successful shared synchronization supplies a migration target, lifecycle and migration index. The runtime follows the applicable procedures, resolves independent authority and records only actual verified adoption in its owned checkpoint. Synchronization and another runtime's adoption provide no adoption evidence for the active runtime.

## Mandatory context and knowledge readiness

Each context response directs the runtime to the shared view. The complete procedures appear at its head, followed by neutral technical adoption guidance. The optional context.instructions.mandatory result distinguishes the prior generated-block state from its actual readback result and identifies the configured source. Resolve the active runtime adopted checkpoint independently; generation is not adoption. Complete context-reference forwarding and native nonblocking continuation remain required. Output overflow is an explicit error, never successful truncation.

A current G2+ organizational subject adds the knowledge module closure. Local technical adoption uses a distinct subject and creates no organizational ticket or profile. Profile creation, publication, semantic coverage and actual application remain obligations of the authorized receiving runtime, not facts established by classification acceptance. Current-state reconciliation preserves usable historical documents, adequate canonical profiles and peer installations; it never invents historical profile usage.

Governed records (G2–G4 in planning, execution or verification, without technical_adoption) declare work_item, domains and knowledge. The controller reads the derived operations/oop-knowledge-index.json (absent means an empty verified index), computes applicable profiles, compares declared revisions and content identities with the index and the actual profile bytes, and applies the step gates of KP-12 for the target state. Failures return knowledge_declaration_missing, knowledge_profile_missing_declaration, knowledge_identity_mismatch, knowledge_step_incomplete or knowledge_domain_unknown as non-accepted records with failing items and a remedy on standard output; an unreadable index is accepted only as receipt.knowledge.status=unverified_store_unavailable. The controller sets receipt.knowledge; a runtime-supplied facet is never knowledge evidence. Context lists knowledge_obligations by reference and never delivers profile text. The separate offline validator dist/oop-knowledge.js is the R14 publication boundary for profiles, the index and work-item records; the controller never denies host operations.

### Knowledge declarations and current obligations

A governed declaration carries knowledge format 1, record_ref and record_identity. record_ref is an operations-relative work-item path; record_identity binds the canonical serialization of its extracted knowledge member. The controller compares actual record content, installation, work item, classification, domains, declarations and current input coverage, then applies the distributed knowledge validator predicates. Missing records, mismatched identities, unclassified current input, missing correction evaluations and stale dependency evidence produce non-accepted records. An unreadable index remains explicitly unverified and cannot establish knowledge readiness. No response grants host authority.

Every prompt supplies context.knowledge_input.reference for the current native turn and a reference to the complete mandatory procedure. Bounded retained governed subjects resolve current records in context.knowledge_obligations, including review status, unresolved events, stale evidence and gaps. Closed or cancelled canonical items retire dynamic obligations. Transparent complete-context adapters need no knowledge parser; strict record/output readers must support the declared knowledge format. Native events and exit conventions remain those of the context interface.
