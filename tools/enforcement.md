# Context controller and runtime adapter

The official controller in `dist/oop-enforce.js` implements `oop-context-1`. The manifest and interface describe the registered workspace, the bounded event envelope and the nonblocking response. Native integrations deliver additional context at supported session-opening and prompt events. Host authorization and effect verification apply independently.

## Filesystem path boundary

Supply a complete native absolute owned runtime root in the argument vector. Serialize dynamic event values with a JSON serializer on standard input; never construct JSON by shell interpolation. Drive-qualified native paths may use forward slashes. Drive-relative paths, current-drive root-relative paths, dot segments, control characters and filesystem aliases are ineligible.

For a non-native vocabulary, the owned registration may contain at most 16 nonoverlapping absolute-prefix mappings in path_mappings. Each entry has from and to; to is native and must resolve inside the authorized filesystem topology. For example, if the observed native drive binding maps /c/ to C:/, an installation may register {"from":"/c/","to":"C:/"}. A host with a different filesystem namespace may instead register its observed drive binding explicitly. No mount root or shell is inferred. A native absolute input keeps its native meaning, and the event cannot choose the mapping. Mappings apply to cwd and registration filesystem locators; operations-relative references, identifiers and immutable content identities retain their contracts. Mapping syntax never establishes ownership or authority, and alias/type/containment checks still apply.

Path failures deliberately keep context.status=context_unavailable as the compatible summary of context availability. Read diagnostic.code for the cause and diagnostic.items for the field, rule, expected form and safe received type; status alone is insufficient to select a repair. Device namespace paths are rejected as device_namespace before checking dot segments; supported extended drive and network-share prefixes retain their native path handling. The actual path and arbitrary exception text are withheld. Repair registration fields under current authority; correct event fields before retrying. Native continuation and user-stop behavior remain independent. Adapters must supply complete paths and consume safe specific diagnostics; contact points and exit dispositions retain their contracts.

workspace path strings, including workspace.cwd, are normalized native spellings and may retain input case. They are not unique canonical resource identifiers. Different strings do not by themselves prove different resources, and raw string equality does not replace scoped filesystem identity and ownership checks. Such checks retain alias, type and containment restrictions; presentation normalization grants no additional access.

The bundled local checkout synchronizer uses one implementation backend and verifies its ordinary checkout with relative root/metadata output. This backend is an implementation choice, not a protocol requirement for all runtimes. It does not support linked worktrees or submodules.

## Operations binding

The owned registration records the repository-scoped operations binding verified at bootstrap as operations_binding {profile, entries:[{entry, key, value}]}; dist/procedures/operations-binding.json maps the abstract entries to a version control system. At session opening and at the first prompt of the day the controller compares the checkout configuration with that record, read-only, and reports operations_binding {status: verified | drift | unavailable | not_recorded, items}. It never blocks or repairs; the runtime restores drifted entries under current authority before effects on operations.

## Daily synchronization and adoption

The first eligible event outside bootstrap inspects the exact configured checkout and synchronizes the selected official revision under a shared lock. The supplied version control implementation preserves branch references, replaces unpersisted checkout state, and leaves separate project data outside the operation. Unsupported topology, unknown ownership, interrupted work or transport failure remain observable. An orphan lock requires authorized reconciliation and evidence that the old writer cannot resume.

Synchronization and another runtime's adoption provide no adoption evidence for the active runtime.

## Mandatory context and knowledge readiness

Each response binds the complete source-bound mandatory procedures, accepted organization/workspace rules and structured tool guidance. The common content identity supports reuse only while complete verified content remains available. The mandatory routing section supplies current-state and reachable-state module closures plus the compact semantic index for conditional scope. Resolve adopted checkpoint applicability independently; content equality is neither adoption nor effect authority. The controller composes instructions in memory without a shared Markdown view or native instruction pointer.

A current G2+ organizational subject adds the knowledge module closure. Local technical adoption uses a distinct subject and creates no organizational ticket or profile. Profile creation, publication, semantic coverage and actual application remain obligations of the authorized receiving runtime, not facts established by classification acceptance. Current-state reconciliation preserves usable historical documents, adequate canonical profiles and peer installations; it never invents historical profile usage.

Governed records (G2–G4 in planning, execution or verification, without technical_adoption) declare work_item, domains and knowledge. The controller reads the derived operations/oop-knowledge-index.json (absent means an empty verified index), computes applicable profiles, compares declared revisions and content identities with the index and the actual profile bytes, and applies the step gates of KP-12 for the target state. Failures return knowledge_declaration_missing, knowledge_profile_missing_declaration, knowledge_identity_mismatch, knowledge_step_incomplete or knowledge_domain_unknown as non-accepted records with failing items and a remedy on standard output; knowledge_record_mismatch lists each differing field in items and details ({field, rule, expected, received}), and knowledge_record_historical names the KP-19 linked reconciliation route for a format-1 record; an unreadable index is accepted only as receipt.knowledge.status=unverified_store_unavailable. The controller sets receipt.knowledge; a runtime-supplied facet is never knowledge evidence. Context lists knowledge_obligations by reference and never delivers profile text. The separate offline validator dist/oop-knowledge.js is the R14 publication boundary for profiles, the index and work-item records; the controller never denies host operations.

### Knowledge declarations and current obligations

A governed declaration carries knowledge format 1, record_ref and record_identity. record_ref is an operations-relative work-item path; record_identity binds the canonical serialization of its extracted knowledge member. The controller compares actual record content, installation, work item, classification, domains, declarations and current input coverage, then applies the distributed knowledge validator predicates. Missing records, mismatched identities, unclassified current input, missing correction evaluations and stale dependency evidence produce non-accepted records. An automated runtime notice without owner content covers the current input with input_coverage status runtime_notice, a reason and no events. A first record of a turn enters execution directly only when the referenced record has the declared work item, this installation_uid, the declared record identity and a valid validated plan; direct verification also requires canonical work in in_progress, executed or verification and no planned step. Otherwise diagnostic.current.continuation names the failed condition and its remedy. An unreadable index remains explicitly unverified and cannot establish knowledge readiness. No response grants host authority.

Every prompt supplies context.knowledge_input.reference for the current native turn and a reference to the complete mandatory procedure. Bounded retained governed subjects resolve current records in context.knowledge_obligations, including review status, unresolved events, stale evidence and gaps. Closed or cancelled canonical items retire dynamic obligations. Transparent complete-context adapters need no knowledge parser; strict record/output readers must support the declared knowledge format. Native events and exit conventions remain those of the context interface.
