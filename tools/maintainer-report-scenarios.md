## Local parser boundary

Supported captured reports use English or Italian ATX terminal headings, consecutive top-level `1.` proposal entries, `PROP-01` onward, metadata `[finding reference; P0–P3; disposition]`, and the six bold labels in template order. Fields may span lines. The two impact dimensions use the supported labels followed by `: STATUS — reason` (also `-`, `–` or `:` separators); declarations are on separate lines or separated with semicolons. Each aggregate dimension cites every proposal ID explicitly; compact ID ranges are outside this parser's supported presentation. Required/unresolved notices use a bold line immediately before the list and cite all proposal IDs. Maintainer appendix edits to PROTOCOL.md must be distinguished in the impact field. Fenced code is excluded from structural recognition. Other locales/formats are unsupported or fail this declared profile and remain NOT VERIFIED; human-facing validity does not depend on using this parser profile.

PASS verifies the presence of nonempty example slots, not their realism; labels and declared impacts, not normative truth; proposal-ID references, not finding authenticity; and aggregate arithmetic, not omission of an undiscovered recommendation. No pre-delivery chat hook is installed. No mandatory framework, consumer validator, network effect or acceptance observation renumbering is introduced.

## FORMALIZE / PREPARE / VERIFY / APPLY procedure captures

The canonical command order is DIAGNOSE, FORMALIZE, PREPARE, VERIFY, APPLY, REPORT. FORMALIZE copies the frozen PREPARE with only two documented exception categories and retains internal REPORT data. PREPARE appends only terminal display and saves; APPLY executes unchanged without publication capability, then explicit outer VERIFY gates every commit. Actual VERIFY and completion report real outcomes. Reading the appendix does not invoke APPLY, and REPORT cannot recurse or launch an audit.

## Overview assessment in generated implementation prompts

The approved FML-C addition extends FORMALIZE beyond its three historical delivery/display corrections without changing the frozen PREPARE preimage. Every generated implementation prompt requires the executor to assess Abstract, Vision, Goal and Introduction, record an update or justified no-change disposition for each, and make necessary explanatory updates. Overview prose cannot create runtime authority or hide a normative change. FML-038 rejects omitted or narrowed assessment instructions through the same exact-copy boundary; these are source-contract checks, not proof that a live AI obeyed a generated prompt.
