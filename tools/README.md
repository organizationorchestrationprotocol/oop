# Maintainer reference mechanisms

Technical audit instructions and the DIAGNOSE, PREPARE and VERIFY commands live in [the repository maintainer appendix](../PROTOCOL.md#rules-for-the-maintainer); see the [maintainer command guidance](../README.md#maintainer-commands).

The complete current-source derived distribution is generated with `node tools/generate-release.mjs`, then accepted locally with `node tools/accept-release.mjs`. The generator exports 35 modules and 54 complete source clauses from an explicit semantic allocation; BOOT-01–13 and lifecycle/interface records formalize execution boundaries without replacing semantic judgment. It stages every output in memory, validates source/schema/dependencies and the complete inventory, then preflights every output path and orphan before any filesystem mutation. Shared path checks reject traversal, symlinks/junctions, non-directory parents, non-file outputs and unsafe JSON orphans. Only obsolete JSON files directly inside `distribution/modules/` and `distribution/details/` are removed; unrelated files are preserved. Producer acceptance runs 69 expected local observations and seven scenarios against the actual package. See `evidence/release-traceability.json` and the acceptance reports described below for scope and limitations. These commands never belong in consumer bootstrap and perform no provider effects or runtime installation.

Acceptance records `evaluated_checkout.commit`, ref, clean/modified working-tree status and exact subject file identities. `source_snapshot_commit` remains the generator's source provenance, not the evaluated HEAD. By default, acceptance writes ignored local `evidence/current-acceptance.json` and `evidence/current-tests.tap`. Run it after the final commit, then run `node tools/accept-release.mjs --check-current` to reject stale HEAD or changed subject content. Commit and push still require explicit user instruction.

For a reviewable committed evidence snapshot, run `node tools/accept-release.mjs --snapshot`; this writes `evidence/release-acceptance.json` and `evidence/release-tests.tap`. That historical report identifies the checkout and file contents evaluated before its evidence commit. It cannot contain the SHA of its own containing commit. The ignored current report identifies the final HEAD without creating another evidence commit. Current generated acceptance/TAP outputs are excluded to avoid self-reference; historical baseline evidence is read from Git and bound by its recorded commit/content identity.

`acceptance-inputs.mjs` is the explicit input inventory and expected observation catalog. The required `Rules for the runtime` and `Rules for the maintainer` sections keep repository maintenance instructions out of normative source reconstruction and consumer context measurements; freshness identities still bind the entire `PROTOCOL.md`. Missing, malformed, duplicate or reordered headings are rejected for the current document. Only historical checkpoint reads accept the older document layout. Extraction retains the document title and runtime rules, omitting the explanatory overview, runtime section heading and maintainer section, preserving the previously reviewed normative text. Allocation and traceability spans use extracted-source line numbers; generated contract locators use actual document line numbers, accounting for the actual length of the overview and runtime heading. It includes both reference fixtures, both candidate JSON inputs, generator/validator dependencies, all invoked suites, traceability, package JSON and applicable validation guidance/workflow. Unrelated files and unused historical prototype scripts are not inputs. `--check-current` only reads: changed HEAD, changed input identities or a false readiness verdict reject the report; a modified working tree with identical subject bytes does not invalidate it. Acceptance checks the complete expected ID set, total/unique counts and PASS/FAIL/SKIP outcomes. Missing, duplicate, unexpected, failed or skipped observations block readiness.

Run `node --test --test-reporter=tap tools/reference-engine.test.mjs tools/release.test.mjs tools/prune-artifacts.test.mjs tools/producer-safety.test.mjs` before final acceptance. The 59 retained observations keep their IDs and assertions. New cases are `REL-TOOL-005` (real freshness command against an equivalent exact identity/commit-bound report fixture; material fixture, validator and candidate changes, restoration, unrelated file and no writes), `006` (output file link), `007` (both module/detail directory links), `008` (evidence directory link), `009` (unsafe orphan directory), `010` (incomplete/colliding/traversing inventory), `011` (late staged-plan preflight error), `012` (isolated deterministic 35-module/54-clause export, safe cleanup and repeat), `013` (orphan file link) and `014` (evidence output file link). Mutation tests copy files and Git history to temporary directories and clean up even on failure; external sentinels remain inside the temporary test sandbox. Unsupported link creation is reported as SKIP, never PASS. Run in a local environment supporting these checks before readiness. The positive export comparison updates the two source-provenance commit fields to evaluated HEAD and the historical source snapshot path to the current canonical filename; all other serialized distribution bytes must match. Do not regenerate the operational `distribution/` merely because producer code changed.

Validated writes use exclusive temporary files beside each destination and controlled rename replacement, followed by validated orphan removal. These safeguards cover unsafe paths present before preflight, not hostile concurrent path mutation or multi-file atomicity. An apply I/O failure reports possible partial file/directory effects and asserts no success/readiness; inspect and reconcile actual effects before rerunning generation and acceptance. A previously existing acceptance becomes stale whenever its subject bytes change.

One optional producer workflow, `.github/workflows/producer-tests.yml`, runs full scoped producer-package acceptance against the current checkout on pull requests and pushes to `main`, then rechecks the generated ignored current report with `--check-current` and displays its test TAP. Acceptance runs the four suites once. Checkout fetches full Git history for the accepted checkpoints and earlier source baseline. Successful CI does not certify publication, consumer adoption or runtime/provider integration. The workflow retains `contents: read`, no persisted credentials, no custom secrets, no deploy or artifact upload, and no generation in the checked-out distribution. It uses the standard Ubuntu runner's Node.js and one GitHub-owned checkout action pinned to a verified commit. A private-repository guard prevents accidental paid execution after a visibility change. Standard hosted runners for public repositories are [free under GitHub's current billing policy](https://docs.github.com/en/actions/concepts/billing-and-usage), subject to [usage limits](https://docs.github.com/en/actions/reference/limits); availability still depends on repository/account Actions policy. No remote run or settings change is implied by preparing this file. After observing a successful run, a maintainer may separately authorize requiring `local-tests` on a protected default branch, current checks before merge and restricted force pushes/deletion. Such protection does not prove semantic review or runtime/provider readiness and need not mandate PR ceremony for every activity; no branch protection is changed here.

`release-plan.mjs` is a reviewed semantic allocation, not a heading/keyword parser. `release-review.json` binds every approved source span and module dependency to the reviewed source. A source change stops generation until complete semantic review updates that ledger and affected mappings/contracts/tests. Preserve stable clause and observation identities; record actual deltas rather than silently assigning new meanings to old IDs. The current acceptance path covers derived-only regeneration of unchanged canonical semantics: changed source against the latest committed accepted checkpoint requires explicit semantic delta/regression work before acceptance. It must not be labeled an empty-delta generation. On the first complete export the preceding committed source/reference checkpoint is used with its narrower evidence scope disclosed; no prior complete distribution or live result is invented.

For a future semantic source change: record the exact source delta and affected clauses/modules; review authority, compatibility for existing readers/writers, migration disposition and recovery; identify the latest-prior valid checkpoint and add regression cases preserving historical IDs. Only after semantic review update allocation/review bindings, regenerate in isolation and evaluate the changed package against that checkpoint before acceptance. The current `generated_derived_only` path explicitly fails `source_preservation` when canonical source differs from its baseline; it does not automatically support normative deltas. Introduce a dedicated delta acceptance path only when a concrete reviewed semantic change requires it and its baseline, impact/migration evidence and regression criteria are specified. Do not bypass the existing source gate to obtain readiness.

The accepted package contains exact semantic source clauses and typed reference boundaries. `$clause` means evaluate that complete clause for the named contract dimension; `$clause+core` also applies Core. It is not a JSON pointer, an automatic boolean conversion or a new authority. Predicates can check necessary attributed facts, but fact authenticity, semantic classification, permissions and installed enforcement remain independently established. Optional native/local implementations may consume these contracts without using the maintainer's Node implementation.

These are local producer fixtures, not an installable OOP distribution, consumer prerequisites or proof of live runtime governance. `PROTOCOL.md` is the only normative source. JSON Schema describes the intended producer contract; the reference engine demonstrates closure, assembly, three-valued guards, selective invalidation, scoped reuse and readiness distinctions. No effects, provider calls, credential enrollment, model calls, installation or repository audit are performed.

Run `node tools/export-candidate.mjs`, then `node --test tools/reference-engine.test.mjs` for isolated positive/negative/unknown scenarios. Run `node tools/benchmark.mjs` for reproducible fixture measurements. These commands belong exclusively to maintenance; do not place them in consumer activation, bootstrap, migration or recovery. Node is a maintainer implementation choice, not a consumer dependency.

`record-evidence.mjs` records the original REL-01–11 change against its original pre-change checkout. It is a retrospective narrow checker, not the new release acceptance command; its original baseline assumptions no longer apply after that source change is committed. Stored historical evidence describes only its recorded subjects.

The fixture catalog and single exported BOOT-11 contract are deliberately incomplete and cannot satisfy REL-02/REL-11. They are not substituted for canonical modules. The restricted schema-profile validator supports only this profile's declared keywords and rejects unsupported features; it is not a general JSON Schema implementation. Its test result applies only to the checked candidate contract. Local test outcomes do not establish complete semantic reading/coverage, installed runtime controls, provider access, cross-runtime compatibility, latest-prior verified regression, publication or consumer adoption. Candidate generation and live adapters require separate complete source-to-derived semantic review and actual integration evidence before distribution readiness.

Historical `fixture-benchmark.json` describes synthetic fixture content only. Acceptance reports measure the real selected package context including entry/selector and applicable procedure bytes, local module reads and selection/read/assembly duration; the comparison is full canonical source loading. Token counts, runtime model calls, end-to-end latency and money remain not_measured. Neither result proves product integration or economic savings. `distribution/entry.json` is the structured entry after scope-bound producer acceptance; it is not a consumer adoption checkpoint or OOP version manifest.

Future economic experiments require an identical workload, provider/runtime/model, equivalent conditions and controls for both full-source and selected-context runs; report cold and warm cases separately. Measure actual tokenizer/billed tokens, model calls, complete end-to-end duration and monetary cost, including retries/recovery and verification overhead, with repeat counts and uncertainty. Record unexercised provider actions as `not_performed` and unavailable metrics as `not_measured`. Such separately authorized experiments must not infer ROI or money saved from local byte reduction; these maintenance commands make no paid AI/provider calls.
